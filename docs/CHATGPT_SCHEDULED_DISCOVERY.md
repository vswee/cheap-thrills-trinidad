# Existing ChatGPT scheduled discovery

Keep the existing ChatGPT research task and its schedule. This repository supplies the publishing instructions the task reads. This flow uses the GitHub plugin and does not need a local checkout or cloud discovery API keys.

On every run:

1. Fetch the latest `public/.well-known/cheap-thrills-contribute.json`, `docs/CONTRIBUTING_FINDS.md`, the matching food/event mandate, `public/schemas/find.schema.json`, and relevant existing records from `vswee/cheap-thrills-trinidad` on `main`. Use current instructions rather than a cached copy.
2. Check for pending contributions using the procedure below before creating any branch. Then research current public sources under the mandate. Deduplicate against both `main` and pending records by ID, slug and underlying event/offer. Update the same record for a material change; preserve its ID, slug and creation date. Record actual check times, claim-specific source support, and the real researcher/model. Leave uncertain dietary details unknown. A still-qualifying pending record can be submitted even when research finds nothing new. With neither qualifying pending work nor new changes, create no branch or PR and stay silent.
3. Resume the existing contribution branch when one is pending. Only when the pending-contribution check is complete and no resumable contribution remains, use the GitHub plugin to create a unique branch from the latest `main`, for example `codex/chatgpt-finds-YYYY-MM-DD-HHMM`. Commit only canonical JSON additions or updates under `content/finds/food/YYYY/` or `content/finds/events/YYYY/`. Keep one run to at most 25 records. Do not include scratch files, schema changes, code, brand assets or deletions.
4. Run the local validator if a shell/checkout is available. Otherwise submit through the plugin and let GitHub's **Validate find records** check run it. The merge job also validates the complete merged directory before publication. Open a non-draft PR targeting `main`, with direct source links, check dates and caveats. The initial authorised PR author is `vswee`.
5. Apply the `agent-content` label using the GitHub plugin's PR labeling action. This is the opt-in for the repository's authorised-agent merge workflow. A PR without the label stays for manual review. Only the configured author allowlist confers authorisation.
6. Inspect the PR checks and state. Fix any validation failures on the same branch. Automatic publication waits for the checks, validates the full merged directory, and merges when it can publish without overwriting a concurrent update. A conflict or an in-progress check can defer merging to the next 15-minute retry.
7. Report the PR URL as **submitted** only after GitHub confirms it exists. Report **published to the repository** only after GitHub confirms it is merged; deployment is a separate state. If submission fails, give the exact failed operation and error, preserve the canonical JSON and existing branch/commit/PR references in the task output, and state which stages succeeded. Say no PR exists only after checking GitHub. Do not imply an integration error is a ChatGPT permission block, or vice versa.

## Resume pending contributions before creating branches

Use GitHub reads to list this flow's `codex/chatgpt-finds-*` branches and associated PRs, including closed PRs. Follow pagination. Inspect the changed files and canonical records relative to current `main`; a matching branch name alone does not authorise modifying someone else's work. If these reads fail or the inventory is incomplete, stop submission without creating a replacement branch.

- For a merged PR or an equivalent record already on `main`, consider that contribution complete. Do not recreate it. Material later corrections update the existing canonical record.
- For an open PR, resume that PR and branch. Inspect its checks and label rather than opening another PR. Do not reopen a closed, unmerged PR or resubmit its records without resolving the reason it was closed.
- For a branch with committed records and no PR, recheck that the records remain current, qualifying and absent from `main`. Confirm the diff is limited to at most 25 canonical JSON additions/updates. Reuse that branch for the required non-draft PR; do not copy its records onto a fresh branch merely because PR creation previously failed.
- If several branches contain the same pending record, prefer an existing open PR. Otherwise use the branch with the most recent source-verified version, preserving the record identity. Do not submit duplicate branches or delete the others automatically. Report incompatible versions for review.
- An empty branch is not a committed contribution. It may be reused only if it belongs to this flow and still points at current `main`; otherwise leave it alone. Conflicts, stale records or unexpected files require resolution on the existing contribution or owner review, not a replacement branch.

Attempt the required PR creation at most once per run. After an uncertain network response, read GitHub to check whether the PR exists before any later retry. If OpenAI action review rejects a write, stop all submission writes for that run, retain the branch and commit, and report the exact rejection. Do not create another branch, switch write tools/endpoints, or change permissions to circumvent that rejection. A later scheduled run may make one authorised attempt on the same pending branch, subject to the same review. New research can be preserved in the task output while publication is blocked.

If the existing task stores its publishing instructions rather than fetching the guide, append this instruction to that task without changing its research mandate or schedule:

> On every run, fetch and follow `docs/CHATGPT_SCHEDULED_DISCOVERY.md` and `public/.well-known/cheap-thrills-contribute.json` from `vswee/cheap-thrills-trinidad` on `main`. Inspect existing `codex/chatgpt-finds-*` branches and PRs before creating a branch. Resume a still-qualifying pending contribution; deduplicate against both pending work and `main`. Attempt the required PR operation once per run. If action review rejects a write, stop submission writes for that run and preserve the existing branch/commit; do not create a replacement branch or switch write mechanisms. Submit qualifying canonical JSON changes through the GitHub plugin and apply `agent-content`. Let repository automation merge after validation and confirm the actual PR state before claiming publication. With no qualifying pending or new work, stay silent.

Repository instructions cannot alter a ChatGPT task that never fetches them. Updating such a stored task prompt requires access to that existing task; it should not create a second schedule.
